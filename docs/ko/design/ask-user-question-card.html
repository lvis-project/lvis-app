LVIS 질문 카드 (Ask-User-Question Card) — 디자인 목업

ask_user_question LLM 도구가 발생시키는 비모달 질문 카드의 디자인 의도 기록. 구현체는 QuestionOverlay.tsx 와 AskUserQuestionCard.tsx 에 존재하며, 채팅 composer dock의 아래쪽 surface에 렌더된다.

1. 디자인 의도 요약

질문 개수 레이아웃 응답 흐름 건너뛰기
1개 단일 폼: 질문 텍스트 + 선택지 칩 단일 선택은 선택지 클릭 시 즉시 respond. 다중 선택은 "보내기" 버튼으로 전송. "건너뛰기" → dismissed: true 로 LLM 에 전달, LLM 은 기본값으로 fallback.
2~4개 페이지네이션 방식. 헤더에 n / total 표기.
마지막 단계 = 검토 화면 (모든 답변 나열, 행 클릭 시 해당 질문으로 복귀). 		다음/이전 → 마지막 단계 → 검토 → 보내기 로 모든 답변 일괄 전송. 어느 단계에서든 "건너뛰기" 시 카드 전체가 닫힘.

2. 시나리오 A — 단일 질문 (1/1)

가장 흔한 경로. LLM 이 3개 선택지를 emit, recommendedIndex: 1 · altIndices: [2] 로 표기. 어느 선택지든 클릭하면 즉시 응답하고 활성 카드는 큐에서 제거되며, 답변 회고 버블이 materialize된다. 사용자 수기 입력 필드는 노출하지 않는다.

"이번 주 회의록 정리 시작할까요?"
오후 2:14
회의록 정리 어떤 형식으로 만들어 드릴까요?
❓ 질문
출력 형식을 골라주세요. 회의 길이가 30분 이상이면 요약형이 더 보기 쉽습니다.
상태 표기 규칙
  • Recommend — 질문당 1개. recommendedIndex 가 둘 이상이어도 첫 번째만 사용.
  • 대안 — 보조 추천. Recommend 와 disjoint, 회색 톤.
  • 선택된 칩 = 파란색 배경. 선택지 라벨은 trim 후 고유해야 하며, UI 상태는 안정적인 키보드 탐색을 위해 인덱스로 추적한다.
  • 선택지는 질문당 1~3개, 각 20자 이하로 제한한다. UI 는 허용 범위 안의 긴 라벨을 줄바꿈해 표시한다.

3. 시나리오 B — 다중 질문 (3개) 페이지네이션

각 질문을 단계별로 진행. 우측 하단 버튼이 다음 → 검토 (마지막 단계) → 보내기 (검토 화면) 로 순환. 이전 으로 복귀 가능. 카드의 step + drafts 상태는 request.id 별로 보존된다.

1단계 / 3 · 회의 길이
❓ 질문· 1 / 3
회의 길이는 어느 정도로 예상하시나요?
2단계 / 3 · 형식
❓ 질문· 2 / 3
출력 형식을 골라주세요.
3단계 / 3 · 공유
❓ 질문· 3 / 3
완성 후 자동 공유할까요?
최종 단계 · 검토 (confirm)
❓ 질문· 검토
모든 답변을 확인한 뒤 보내기를 누르세요. 항목을 클릭하면 해당 질문으로 돌아갑니다.
검토 행 라벨: 모델이 summaryHint 를 제공한 경우 그 값 (한국어 ≤ 10자 권고). 누락 시 question 을 약 14자에서 잘라서 사용 (truncateForLabel). 미응답 행은 답변 텍스트가 amber 색으로 표시.

4. 시나리오 C — 답변 완료 후 회고 버블

현행 계약: 응답 성공 시 활성 질문 카드는 큐에서 제거되고, ask_user_answer entry가 읽기 전용 답변 회고 버블 로 user-bubble 우측에 렌더된다. 이 entry는 채팅 history에 저장되어 스크롤 / 세션 reload 후에도 응답 내용이 보존된다.

회의록 정리 어떤 형식으로 만들어 드릴까요?

구현 메모:
  • onResolved(request.id)는 활성 카드를 askQuestions 큐에서 제거한다.
  • chat-stream-state.ts가 tool result를 kind: "ask_user_answer" entry로 materialize하고, AskUserAnswerBubble이 이를 렌더한다.
  • 카드의 resolved 복제본은 남기지 않는다. 사용자가 다시 보는 영구 표면은 답변 회고 버블 하나다.
  • 다중 질문은 한 번의 respondAskUserQuestion 호출과 한 개의 회고 버블 안 라벨/값 행 N개로 보존된다.

5. IPC + 상태 컨트랙트

이벤트 페이로드 UI 동작
ask_user_question 도구 emit {id, questions[], createdAt} FIFO 큐에 추가하고 QuestionOverlay가 head 한 건을 composer dock에 마운트.
단일 질문에서 선택지 클릭 respondAskUserQuestion({requestId, answers: [{choice}]}) 응답 성공 시 활성 카드 제거 → ask_user_answer 회고 버블 생성.
다중 질문 보내기 respondAskUserQuestion({requestId, answers: [{choice or choices}, ...]}) 한 번의 IPC 호출로 모든 답변 일괄 전송. 회고 버블 한 개에 행 N개 표시.
건너뛰기 respondAskUserQuestion({requestId, dismissed: true}) LLM tool_result dismissed: true → 기본값 fallback 및 dismissed 회고 버블 표시.

6. 미해결 디자인 메모

  • 선택형 응답 고정. 질문마다 구체적인 선택지 1~3개를 제공하고 사용자 수기 입력 필드는 두지 않는다.
  • label 자체에 뱃지 baked-in 금지. 모델은 20자 이하의 고유한 평문 선택지만 emit하고, Recommend / 대안 표기는 recommendedIndex · altIndices 로 시각만 분리한다.
  • 인덱스 기반 선택 상태. 라벨 문자열과 렌더 순서를 분리해 키보드 이동과 선택 상태를 안정적으로 유지한다.
  • request.id 별 상태 보존. 같은 id 로 재마운트되면 step + drafts 보존, 새 id 면 초기화.
  • 비모달 dock 배치. 카드는 ChatComposerDock의 아래쪽 QuestionOverlay에 위치한다. viewport 전역 modal, backdrop, focus trap 없이 현재 대화 맥락과 composer를 함께 유지한다.
  • 답변 회고 버블. ask_user_answer entry로 현재 구현되어 응답/건너뛰기 결과를 세션 reload 후에도 보여준다.
